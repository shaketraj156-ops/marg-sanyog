# Deploying MARG SANYOG (backend on Render, frontend on Vercel)

**Status: written from reading the code. Nothing here has been deployed or run on Postgres yet.**
Everything in the project was tested on SQLite only. Treat the first deployment as a test.

All data is synthetic. Do not put real railway data into a public deployment.

## The shape of it

```
Browser --> Vercel (static React build, frontend/)
   |
   '------> Render (FastAPI + solver, backend/) --> Postgres (Supabase, Render or other)
```

## Why these choices

- The backend cannot run on serverless functions: the solver is CPU heavy and runs in a background thread and a
  child process. It needs a server that stays up.
- Run **one worker**. "One solve at a time" is enforced inside the process, so several workers or instances
  break it.
- Do not keep SQLite on Render's free plan: its disk is wiped on every deploy, restart and sleep. Use Postgres.
- Trained ML model files go to `backend/models/` on the local disk. On a host without a persistent disk they
  are lost on restart. The planner then falls back to train counts; train again if you need the delay model.

## Steps

### 1. Database (once)

Create a Postgres database (for example a Supabase project). Use a connection string of the form
`postgresql+psycopg://USER:PASSWORD@HOST:5432/DBNAME`.

- With Supabase use the **direct connection or the session pooler (port 5432)**. Avoid the transaction pooler
  (port 6543): psycopg's prepared statements can fail behind it. Check the current Supabase documentation,
  and whether your host needs the pooler (the direct host may be IPv6 only).
- Put the URL in your shell only. Never commit it.

From `backend/` on your own machine, point the app at that database and create the tables and demo users:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://..."
$env:JWT_SECRET = "anything-for-this-one-off-run"
.\.venv\Scripts\python -m alembic upgrade head          # first real test of the migrations on Postgres
$env:SEED_PASSWORD = "a-strong-password-you-will-share-with-judges"
.\.venv\Scripts\python -m scripts.seed_synthetic
.\.venv\Scripts\python -m scripts.load_demo_data        # optional: 16 demo requests and traffic
Remove-Item Env:SEED_PASSWORD, Env:DATABASE_URL, Env:JWT_SECRET
```

If `alembic upgrade head` fails on Postgres, stop and fix that first (the custom column types in
`app/db/base.py` were only ever used on SQLite).

### 2. Backend on Render

Create a Blueprint from `render.yaml` (or a Web Service with the same settings): root directory `backend`,
build `pip install .`, start command as in `render.yaml`. Then set these environment variables:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Postgres URL from step 1 |
| `CORS_ORIGINS` | your exact Vercel address, for example `https://your-app.vercel.app`. A JSON list (`["https://..."]`) or several addresses separated by commas also work; a slash at the end is removed |
| `JWT_SECRET` | generated by the Blueprint (the app refuses to start without it) |
| `SOLVER_WORKERS` | `2` is a safe start on a small plan |
| `DEMO_LOGIN_EMAIL` | `viewer@blockplanner.test` turns on the **Try the demo (read-only)** button on the login page, so visitors and judges need no password. Only an active viewer account is ever used, so a wrong value cannot give more than read access. Leave it empty to turn the button off |

Check `https://<your-service>.onrender.com/health` and `/docs`.

### 3. Frontend on Vercel

Import the repository and set **Root Directory = `frontend`**. Build command `npm run build`, output `dist`.
Set the environment variable `VITE_API_URL=https://<your-service>.onrender.com` **before the build**: Vite
bakes it into the files, so changing it later needs a new build. `frontend/vercel.json` makes every route fall
back to `index.html`, so a refresh on `/dashboard` works.

Then put the Vercel address into Render's `CORS_ORIGINS` (step 2) if you did not know it yet.

### 4. Try it

Open the Vercel address, sign in as `planner@blockplanner.test` with the seed password, run a plan, approve and
publish it, and open the calendar. Also try a wrong password to see the plain error message.

## Before you make it public

- **Passwords.** With `DEMO_LOGIN_EMAIL` set, visitors use the one-click read-only demo and the login page no
  longer lists the demo accounts or hints at the seed password. Keep the planner and admin passwords private:
  they can run, approve and publish plans. Without `DEMO_LOGIN_EMAIL` the page still lists the demo emails and
  says everyone shares the seed password, which is only fine for local use.
- **Secrets.** `JWT_SECRET` must be long and random. Never commit `.env`, a database file or a connection string.
- **`/docs` is public.** The interactive API documentation lists every endpoint. That is fine for a demo.
- **Free plans.** Render's free service sleeps when idle, so open the site a few minutes before a demo. Its CPU
  and memory are small, so a 30 second plan may take its full time limit. Check memory use with OR-Tools and
  scikit-learn loaded.
- **Login limits.** Failed logins lock an email out for 15 minutes after 5 attempts, and each client address is
  limited to 10 attempts a minute. People behind the same network share an address.
- **Backups.** Use the database provider's backup tools. This project has none of its own.

## Not verified

- The migrations and the code on Postgres.
- That `render.yaml` and the Python version in it are accepted by Render as written.
- Memory and speed on free hosting plans.
- The Docker files in this repo (`docker-compose.yml`, `backend/docker/Dockerfile.api`): they come from an
  earlier design that also lists Redis, which the project does not use. This guide does not need them.
